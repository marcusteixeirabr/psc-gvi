## Story

**Para que** tenhamos a espinha dorsal da aplicação funcionando antes de implementar qualquer feature.

## Contexto

Esta story monta o esqueleto que todas as outras stories vão usar:

```
Requisição HTTP → Gin (roteador) → Handler → Service → DB (pgx)
```

Em Go não existe um framework que "magicamente" conecta tudo como o Spring Boot.  
Você escreve o `main.go` explicitamente — o que é ótimo para aprender porque você **vê** cada peça sendo montada.

### Por que pgx em vez de database/sql?

`pgx` é o driver PostgreSQL nativo para Go. É mais rápido e suporta tipos PostgreSQL que o `database/sql` genérico não suporta (ex: `TIMESTAMPTZ`, `DECIMAL`). Usaremos `pgx/v5` com pool de conexões.

### Por que godotenv?

Lê o arquivo `.env` e injeta as variáveis no ambiente antes da aplicação iniciar. Em produção (GCP) não usamos `.env` — as variáveis já existem no ambiente. O `godotenv` só age se o arquivo existir.

## Dev Notes

### Estrutura de arquivos desta story

```
cmd/
└── server/
    └── main.go          ← ponto de entrada da aplicação

internal/
├── config/
│   └── config.go        ← lê variáveis de ambiente, retorna struct Config
└── db/
    └── db.go            ← cria e retorna o pool de conexões pgx
```

### Conceito: fail fast

Se a aplicação não consegue conectar ao banco na inicialização, ela deve encerrar imediatamente com uma mensagem de erro clara — não tentar continuar "esperando" o banco aparecer. Isso é chamado de *fail fast* e evita que a aplicação suba em estado inconsistente.

### Conceito: pool de conexões

Abrir uma nova conexão com o banco a cada requisição HTTP é lento (~50ms).  
Um pool mantém um conjunto de conexões abertas e as reutiliza. O pgx faz isso automaticamente via `pgxpool.New`.
