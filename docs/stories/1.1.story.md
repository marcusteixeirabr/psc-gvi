## Story

**Como** desenvolvedor do psc-gvi,  
**Quero** que o schema completo do banco de dados seja criado via migrations versionadas,  
**Para que** todas as tabelas, constraints e dados iniciais existam antes de qualquer código de aplicação.

## Contexto

Em Go com `sqlc`, o SQL **é** o domínio. Não existe ORM com anotações como no Java (`@Entity`, `@Column`) — você escreve o `CREATE TABLE` diretamente, e o `sqlc` lê esses arquivos para gerar structs e funções Go automaticamente. Isso significa que **a qualidade do schema define a qualidade de todo o sistema**.

`goose` é o gerenciador de migrations: cada migration é um arquivo `.sql` numerado e versionado. O goose registra quais migrations já foram executadas na tabela `goose_db_version`, garantindo que o schema evolua de forma segura e reproduzível.

## Domínio modelado

Baseado na análise do projeto Java legado (`port-inspection-control`) e no scraper (`praticagem-itajai-proxy`):

| Tabela | Representa |
|--------|-----------|
| `users` | Usuários do sistema (auth + RBAC). Unifica `Usuario` e `Inspetor` do Java — são apenas 5 pessoas, não faz sentido separar. |
| `vessels` | Navios cadastrados. Equivale ao `Vessel` Java. O campo `imo` é imutável e único no mundo — é o "CPF" do navio. |
| `port_calls` | Escalas no porto (vindas do ZP-21 ou registradas manualmente). Equivale ao `PortCall` Java. |
| `inspections` | Inspeções PSC realizadas. Substitui o `Inspecao` Java (que era muito simplificado). |

## Dev Notes

### Por que `goose` e não migrations manuais?

Sem goose, você precisaria rodar SQL manualmente em cada ambiente (dev, produção, etc.) e torcer para não esquecer nada. Com goose, `goose up` faz tudo — em qualquer ambiente, sempre na ordem certa.

### Estrutura de um arquivo goose

```sql
-- +goose Up        ← SQL executado ao rodar "goose up"
CREATE TABLE ...;

-- +goose Down      ← SQL executado ao rodar "goose down" (rollback)
DROP TABLE ...;
```

### Tipos PostgreSQL usados

| Tipo SQL | Equivalente Go (sqlc) | Quando usar |
|----------|----------------------|-------------|
| `BIGSERIAL` | `int64` | ID auto-incremento |
| `VARCHAR(n)` | `string` | Texto com limite |
| `TEXT` | `string` | Texto livre sem limite |
| `BOOLEAN` | `bool` | Verdadeiro/falso |
| `DATE` | `time.Time` | Apenas data (sem hora) |
| `TIME` | `time.Time` | Apenas hora (sem data) |
| `TIMESTAMPTZ` | `time.Time` | Data+hora com fuso horário |
| `DECIMAL(p,s)` | `string` (pgtype) | Precisão exata (dimensões) |
| `CHECK (...)` | validação no DB | Restringe valores permitidos |

### Regra de negócio: risk_level e priority

O `risk_level` de um navio é calculado pela idade (do Java `GrauRisco`):
- `high` → mais de 20 anos
- `standard` → 10 a 20 anos
- `low` → menos de 10 anos

O `priority` de uma inspeção é calculado pelo `CialaPolicy` Java:
- `P0` → sem prioridade (dentro do prazo)
- `P1` → prioridade máxima (vencido)
- `P2` → atenção (próximo do vencimento)

Esses valores são armazenados como snapshots no `port_call` — o risco no momento da escala, não o atual.
