# Story 1.3 — Autenticação (login/sessão/RBAC)

## Status: Done

## Story

**Como** usuário do sistema,  
**Quero** fazer login com usuário e senha,  
**Para que** apenas pessoas autorizadas acessem o sistema e cada uma veja o que seu papel permite.

## Contexto

Auth simples: sessão em cookie assinado + RBAC por role. Sem OAuth, sem JWT.

Fluxo completo:
```
GET  /login  → exibe formulário
POST /login  → valida credenciais → cria sessão → redireciona
POST /logout → destrói sessão → redireciona para /login
```

Rotas protegidas verificam a sessão via middleware antes de chegar ao handler.

### Como a sessão funciona (gorilla/sessions + cookie)

A sessão é armazenada em um **cookie no navegador**, criptografada e assinada com `SESSION_SECRET`. Isso significa:
- Não guardamos sessão no banco (sem tabela `sessions`)
- O servidor é stateless — qualquer instância pode validar o cookie
- O cookie não pode ser forjado (assinado) nem lido pelo usuário (criptografado)

### RBAC (Role-Based Access Control)

Dois middlewares Gin:
- `RequireAuth` → qualquer rota protegida; redireciona para `/login` se não autenticado
- `RequireRole("admin", "editor")` → restringe por role; retorna 403 se não autorizado

## Dev Notes

### bcrypt — por que nunca armazena senha em texto puro

O bcrypt transforma "admin123" em "$2a$10$92IXU..." de forma irreversível.
Na validação, ele repete o processo e compara os resultados — nunca "decripta".
Mesmo que o banco seja comprometido, as senhas estão seguras.

### Context do Gin — passando dados entre middlewares e handlers

O middleware autentica o usuário e coloca os dados no contexto:
```go
c.Set("user", userSession)   // middleware escreve
user := c.MustGet("user")    // handler lê
```
Isso evita requerir ao banco de dados em cada handler.
